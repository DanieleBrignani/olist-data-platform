# Observability

Design: [ADR-0007](adr/0007-metrics-from-metadata-tables.md). Code:
`src/olist_platform/observability/exporter.py`, `monitoring/`.

```
pipeline (Prefect flow) ──► meta.* tables (system of record) ──► metrics-exporter ──► Prometheus ──► Grafana
        │                                                         (olist_monitor,      (recording +
        └──► structured JSON logs: stdout + logs/pipeline.jsonl    read-only)           alert rules)
```

## Structured logs

Every line, from our code *and* from third-party libraries, is one JSON object. Each has
`timestamp`, `level`, `logger`, `event` and `environment`, plus the run context bound with
contextvars. Where they apply, fields include `pipeline_run_id`, `flow`, `task`, `source`,
`table`, `rows_read`, `rows_written`, `rows_rejected`, `duration_ms`, `status`, `error_type`
and `severity`. Database numerics are serialised as JSON numbers.

Logs are not shipped to Grafana (no Loki; see ADR-0007). The events that matter operationally
are also persisted in `meta.ingestion_events`, `meta.pipeline_runs` and `meta.dq_results`, so
they can be queried with SQL and are what the metrics are derived from.

## Metrics

| Metric | Type | Labels | Source |
|--------|------|--------|--------|
| `pipeline_runs_total` | counter | flow, status | finished rows in `meta.pipeline_runs` |
| `pipeline_failures_total` | counter | flow, failed_task, error_type | failed runs |
| `pipeline_duration_seconds` | histogram (30 s … 2 h buckets) | flow | `finished_at - started_at` |
| `pipeline_last_run_duration_seconds` | gauge | flow, status | most recent finished run |
| `pipeline_runs_in_progress` | gauge | flow | runs with status `running` |
| `rows_processed_total` | counter | stage (`ingest_raw`/`load_staging`), source | `meta.ingestion_events` |
| `rows_rejected_total` | counter | layer, source, rule, severity | quarantined records |
| `rows_flagged_total` | counter | layer, source, rule | WARNING records kept in the data |
| `data_quality_failures_total` | counter | rule, model, severity, blocking | failed rule evaluations in `meta.dq_results` |
| `quality_gate_last_decision` | gauge | – | 1 PASS / 0 FAIL |
| `dataset_last_published_timestamp_seconds` | gauge | – | `meta.publications` |
| `source_max_event_timestamp_seconds` | gauge | – | latest purchase in the published data |
| `olist_exporter_db_up` | gauge | – | 0 when the metadata cannot be read (the scrape still succeeds) |
| **`dataset_freshness_seconds`** | recording rule | – | `time() - dataset_last_published_timestamp_seconds` |

**Why not Pushgateway:** each process would *replace* the previous counter value, so totals
would not accumulate across batch runs. The metadata tables are append-only, so counters
derived from them are monotonic by construction, survive exporter restarts, and agree with SQL.

**Freshness means warehouse freshness**, not business-event recency. Olist's orders end in
2018. That horizon is shown on its own panel so a "5-year-old data" reading is never mistaken
for a broken pipeline.

## Alerts (`monitoring/prometheus/rules.yml`)

| Alert | Condition | Severity |
|-------|-----------|----------|
| `OlistPipelineFailed` | any new failure in the last hour | critical |
| `OlistQualityGateFailed` | last gate decision is FAIL | critical |
| `OlistDatasetStale` | freshness > 26 h for 10 min (assumes a daily schedule) | warning |
| `OlistMetricsUnavailable` | exporter down or metadata DB unreachable for 5 min | warning |

Rules are evaluated and visible in Prometheus (http://localhost:9090/alerts). Routing
notifications (Alertmanager) is outside the scope of this local platform.

## Dashboard

Grafana (http://localhost:3000, anonymous *viewer* for the local demo) provisions
`Olist pipeline` from `monitoring/grafana/dashboards/olist_pipeline.json`. That file is
generated by `scripts/build_dashboard.py`.

| Row | Panels |
|-----|--------|
| Headlines (stat tiles) | pipeline success rate · last quality gate (PASS/FAIL) · warehouse freshness · last refresh duration · source data horizon · metrics source up |
| Runs | finished runs by flow and status · run duration p50/p95 · failures by task and error type |
| Data | rows processed by source · quarantined/flagged records by rule · data-quality failures by severity |

Status colours (good/warning/critical) are used only for states and always come with a text
value (PASS/FAIL, UP/DOWN).

**Drift guard:** `tests/unit/test_observability_config.py` fails if any panel or rule
references a metric the exporter does not produce, or if the committed dashboard differs from
its generator.
