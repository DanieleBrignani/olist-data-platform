# Production-readiness review (Phase 14)

**Scope:** the whole repository, audited against the brief's Definition of Done and its
requirements. Every "met" claim points to evidence that can be re-run. Anything not met is
stated as such, with the reason.

**Verdict:** ready as a **reproducible, single-node analytical platform**. Every
Definition-of-Done item is met and evidenced, except that CI has not yet run on GitHub: the
repository has never been pushed, so the only evidence is a local rehearsal of the `test` job.
It is *not* a highly available production deployment; the gap is itemised in the last section.

## 4. Changes made by this review

| Finding | Risk | Change |
|---------|------|--------|
| `pipeline-worker`/`metrics-exporter` had no `build:`; they relied on an image built by another service | a fresh clone could try to pull a non-existent image | both build the runtime image themselves; verified by the `--no-cache` clone |
| Prometheus, Grafana and the worker had no healthcheck | `up --wait` could report success for a broken stack | healthchecks on every long-running service (worker: can reach the Prefect API) |
| Host ports hard-coded (except Postgres) | cannot coexist with a local Grafana/Prometheus or a second stack | `*_HOST_PORT` variables with the previous values as defaults |
| Docker json-file logs unbounded | a long-running worker fills the disk | rotation on every service (10 MB × 5) |
| Image names fixed | cannot build side by side / push to a registry | `OLIST_IMAGE_PREFIX` |
| README §9 claimed "40+ tests" | inaccurate claim | corrected to the measured 36 |
| `database_design.md` promised a warehouse index re-measurement that never happened | unfulfilled promise stated as future work | states exactly what was measured |
| `architecture.md` still said "Phase 1 design" | stale status | updated |

## 5. Risk register

| Risk | Likelihood | Impact | In place | Residual / next step |
|------|-----------|--------|----------|----------------------|
| PostgreSQL volume loss | low (local) | total loss of warehouse and history | raw files + lock allow a full rebuild (~90 s benchmark); metadata history would be lost | scheduled `pg_dump` / managed DB with PITR |
| Kaggle unavailable or dataset removed | low | new environments cannot bootstrap | any local copy is accepted if it matches the lock; CI caches by lock hash | mirror the archive in object storage |
| Source schema change in a new version | medium over time | load blocked | breaking changes fail before writes; non-breaking are logged | versioned contracts per dataset version |
| Silent bad data | low | wrong business decisions | contracts + 36 classified dbt tests + reconciliation to the cent + gate before publication | add row-count anomaly checks per table |
| Concurrent refreshes racing the swap | low | failed publication | deployment `limit=1`; swap in one transaction with `lock_timeout` | – |
| Long report blocking publication | medium | delayed refresh | `lock_timeout` → transient → bounded retries; reporting `statement_timeout 60s` | – |
| Credential leak | low | data exposure | per-role secrets, reporting read-only on published schemas only, secret scan before commits | secrets manager, rotation |
| Metadata tables grow without bound | certain over time | slower scrapes, disk | indexes on hot paths | retention policy for `ingestion_events` / `rejected_records` samples |
| Unauthenticated local UIs (Prefect, Grafana viewer) | – locally | exposure if ports are opened | all ports bound to 127.0.0.1 | auth/SSO before any shared deployment |

## 6. Runbook

| Task | Command |
|------|---------|
| Start everything | `docker compose up -d --wait` |
| Run a refresh | `docker compose exec pipeline-worker prefect deployment run olist_refresh/olist-refresh` |
| Why did a run fail? | `SELECT failed_task, error_type, error_message FROM meta.pipeline_runs ORDER BY started_at DESC LIMIT 5;` then Grafana "Failures by task" |
| What was quarantined? | `SELECT layer, source_table, rule_name, severity, reason, raw_record FROM meta.rejected_records WHERE pipeline_run_id = '<id>';` |
| Why did the gate fail? | `SELECT reasons FROM meta.quality_gate_decisions WHERE pipeline_run_id = '<id>';` and the full failing rows in `dq_failures.<test>` |
| Undo a bad publication | `docker compose run --rm dev olist rollback-publish` |
| Reload a file | `docker compose run --rm dev olist ingest --force-reload` |
| Verify two environments match | `docker compose run --rm dev olist fingerprint` on both, then diff |
| Downgrade migrations below 0003 | `olist db drop-derived --yes`, then `alembic downgrade <rev>` |

## 7. From here to a production deployment

Not built, deliberately: they need infrastructure a reviewer cannot run locally, and faking them
would contradict the brief.

1. Managed PostgreSQL with backups/PITR and a replica for reporting.
2. Secrets manager instead of `.env`; credential rotation.
3. Authentication in front of Prefect and Grafana; alert routing (Alertmanager → on-call).
4. Image registry + CD (the `OLIST_IMAGE_PREFIX` and `images` CI job are the hooks).
5. Incremental staging per changed file: the measured bottleneck of a rerun (§12 of the README).
6. Retention policies for metadata and quarantine samples.
7. A work pool with more than one worker, if refreshes ever need to overlap across datasets.
