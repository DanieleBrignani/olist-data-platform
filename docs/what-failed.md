# What Failed and What I Changed (running log)

Entries are appended as they happen during development; README section 16 summarises them.

| Phase | What failed | Root cause | Change |
|-------|-------------|------------|--------|
| 2 | `migrate` container exited 1: `PermissionError: 'logs'` | Runtime image runs as non-root `olist` (uid 10001) but `/app` is root-owned, so the JSON log file directory could not be created | Dockerfile creates `/app/logs` owned by `olist`; the rest of `/app` stays read-only for the app user |
| 3 | Profiling crashed: `'product_category_name' is not in list` | `product_category_name_translation.csv` starts with a UTF-8 BOM, so a plain UTF-8 reader sees the column as `<U+FEFF>product_category_name`. A naive header check would have reported a false breaking change on the real data | The contract format now declares `encoding` per file (`utf-8-sig` for this file only), and BOM appearing or disappearing is itself a breaking change |
| 3 | First contract draft would have typed zip prefixes as integers (the profiler inferred `int`) | The values have significant leading zeros (`01003`) | Zip prefixes are `text` with pattern `^[0-9]{5}$`; a unit test guards it |
| 4 | A unit test asserting the default database name failed only when run together with the integration suite | The integration conftest points the whole process at `olist_dw_test`, which leaked into an unrelated unit test | Unit tests that check defaults now remove the variable explicitly. The separate test database stays: the integration tests truncate tables and must never touch real data |
| 4 | Lint (`S608`) flagged table names interpolated into SQL | Contract `table` values were not validated, so a malicious or mistyped contract could inject SQL | The contract model now accepts only `^[a-z][a-z0-9_]*$` table names, with a regression test |
| 5 | The first real `olist stage` failed: `permission denied to create temporary tables` | The bootstrap revokes every database privilege from `PUBLIC`, `TEMPORARY` included; the staging engine evaluates rules in temp tables | Migration `0004` grants `TEMPORARY` to `olist_pipeline` only; a test asserts the reporting and monitor roles still lack it. The run was correctly marked failed at `load_staging` and not retried |
| 5 | Staging was slow: geolocation alone took 15.8 s | `CROSS JOIN LATERAL (VALUES …)` produced one candidate row per check per record (about 10 M rows) and built a reason string for each | A boolean prefilter runs first, so the expansion only touches violating records: geolocation now takes 2.9 s, with identical outputs (verified by the pinned real-data test) |
| 5 | A reject-ratio test failed | The test expected one rejected table, but quarantining a seller correctly cascades to its order item, so two tables exceeded their limits | The test now asserts the cascade; the engine was right |
| 6 | Two fact models failed under `dbt run`: `could not resize shared memory segment ... No space left on device` | Docker gives containers a 64 MB `/dev/shm`; with 4 dbt threads running parallel hash joins at once, PostgreSQL ran out of dynamic shared memory | `shm_size: 256mb` on the postgres service. This is a deployment setting, not a query change |
| 6 | Integration tests could not read the dbt output: `permission denied for schema marts_build` | The build schemas are owned by `olist_pipeline`; the admin role is deliberately not a superuser | Tests read build schemas as the owning role; a new test asserts the reporting role cannot read any unpublished schema |
| 6 | `dbt --profiles-dir /app/dbt` resolved to `C:/Program Files/Git/app/dbt` | Git Bash on Windows rewrites POSIX-looking arguments passed to `docker compose run` | `DBT_PROFILES_DIR` / `DBT_PROJECT_DIR` are set in the compose service environment, so no path is passed on the command line |
| 7 | The first draft of the reconciliation test would have blocked every run that quarantined an order | It compared all persons in `src.customers` with `dim_customer`, but a customer whose only order was quarantined legitimately stays in `src` without an order | The invariant is now "persons *with an order*", found by reasoning through the quarantine cascade before running it |
| 7 | While measuring rules, ad-hoc queries ran for 26 minutes and PostgreSQL sat at 100% CPU | `timeout` killed only the `psql` client; the server kept executing the abandoned queries. The host was also memory-starved (about 1.2 GB free) and another project's database container was using a full core | The stuck queries were cancelled with `pg_cancel_backend`. Ad-hoc sessions now always set `PGOPTIONS='-c statement_timeout=60s'`, so an abandoned client can never leave work running |
| 7 | While writing `publish_marts` I found that the demoted `*_prev` schemas would stay readable by the reporting role | Schema privileges travel with the schema through `ALTER SCHEMA ... RENAME` | The swap revokes reporting access from the schema being demoted, in the same transaction; an integration test asserts it |
| 8 | The metrics event of the first real orchestrated run logged `"rows_written": "Decimal('1289091')"` | PostgreSQL `sum()` returns `numeric` (Python `Decimal`), and the JSON renderer fell back to `repr()`, so any log consumer would get strings instead of numbers | The JSON renderer serialises `Decimal` as a number and UUID/datetime as strings; a unit test pins it |
| 8 | `logs/pipeline.jsonl` stopped being valid JSON Lines: raw `HTTP Request: POST .../api/logs/` lines appeared | Records from third-party stdlib loggers (Prefect's `httpx` client) bypassed structlog and were written with `%(message)s` | All stdlib records go through structlog's `ProcessorFormatter`, so foreign loggers become JSON with `logger`/`environment` fields; `httpx`/`httpcore`/`urllib3` are set to WARNING. A test asserts every file line parses as JSON |
| 8 | (Design review, not a runtime failure) Prefect's default task caching could skip a pipeline step whose inputs look identical to a previous run's | Orchestrator caching is meant for pure computations; these steps have side effects | Every task uses `cache_policy=NO_CACHE`, asserted by a unit test. Idempotency comes from the data layer, not from caching |
| 8 | The e2e tests could not find the `clean_db` fixture | DB fixtures lived in the integration conftest only | The e2e conftest imports them, which also redirects the whole process to the isolated `olist_dw_test` database, so an e2e flow can never write to real data |
| 9 | The drift-guard test flagged `olist_refresh` as an unknown metric | Its regex also matched quoted label values inside PromQL selectors | Quoted strings are stripped before extracting metric names |
| 9 | On the live dashboard, "Quarantined and flagged records by rule" showed *No rows* although 12 flagged series existed | A Grafana table shows ONE data frame at a time; its first query (quarantined records) is legitimately empty on real data, which hid the flagged records of the second query. No test could see it: the data was correct, the rendering was not | Table queries use table format plus a `merge` + `organize` transformation; a regression test requires `merge` on every multi-query table. Found only because the dashboard was actually opened and read |
| 9 | After a Grafana restart the dashboard was empty for minutes: `plugin prometheus not found` | Grafana 13 ships data sources as external plugins that a background installer downloads from grafana.com at every start and auto-updates (the log showed `zipkin 12.4.6 -> 12.4.8`). The dashboard depended on the network and on a floating plugin version | `docker/grafana.Dockerfile` bakes `prometheus@13.2.1` in at build time; startup preinstall and auto-update are disabled, so Grafana starts offline and deterministically |
| 11 | Migration downgrade past `0003` failed: `cannot drop table src.order_reviews because other objects depend on it` | dbt's `stg` views depend on `src`, and the admin role (not the owner of dbt schemas, not a superuser) correctly cannot cascade-drop them. The migrations had only ever been applied upwards | The failed downgrade rolled back cleanly. `olist db drop-derived --yes` drops the rebuildable dbt schemas as their owner; CI proves the migration code is reversible on a fresh database (upgrade → downgrade base → upgrade) |
| 11 | `alembic` CLI printed nothing, even on success | `migrations/env.py` never loaded `alembic.ini`'s logging config | `fileConfig` is applied when run from the plain CLI; under `olist db upgrade` the JSON logging is kept |
| 11 | The first `git add` staged a 2 MB junk `dbt/C:/Users/.../dbt-ci` directory | Git Bash rewrote `--target-path /tmp/dbt-ci` into a Windows path, so dbt created it inside the repo | Caught by a pre-commit size and content check; removed before the first commit. `.coverage`/`coverage.xml`/`reports/` are now ignored |
| 11 | Running the dev container as another uid hit `PermissionError: /app/logs/pipeline.jsonl` | On Linux the bind-mounted checkout belongs to the runner's uid, not the image's 10001. Docker Desktop hides this | The dev service runs as `${DEV_UID}:${DEV_GID}` (CI sets them from `id -u`/`id -g`) with `PREFECT_HOME` in `/tmp`; the whole CI test job was simulated on a clean checkout as uid 1001 |
| 12 | The benchmark would have recorded the git commit as `n/a` in every run | It called `git rev-parse` inside the container, whose image has no git; lint flagged the subprocess call (`S607`) and investigating it exposed the real bug | The host passes the commit via `BENCHMARK_GIT_COMMIT`; the recorded commit (`dee7d90`) is verified in the generated report |
| 12 | (Finding, not a defect) A rerun with unchanged files still costs most of an initial load | Checksum skip removes ingestion, but staging and dbt rebuild everything by design (full refresh, ADR-0006) | Documented as a measured trade-off; making staging incremental per changed file is the first optimisation target |
